# /spec F-xx — 기능 spec 작성

구현 전에 "무엇이 완료인가"를 **테스트 가능한 문장**으로 고정한다. 코드를 쓰지 않는다.

## 절차

1. **입력 확인**: 인자로 기능 ID(F-xx)를 받는다. 없으면 기획서 기능 목록에서 **내 영역**(`docs/기획서.md` 4절 역할 분담, PC id `dh`=A·`js`=B)의 다음 순서(마일스톤 기준)를 제안한다. 상대 영역 기능이면 사용자에게 확인한다.
   이미 `docs/specs/F-xx-*.md`가 있으면 새로 만들지 않고 그 파일을 갱신한다.
   - 인자가 `approve F-xx`이면 아래 가드 없이 7단계(승인 처리)만 한다.
   - **다른 브랜치에서 진행 중인지 먼저 본다**: `node scripts/branches.mjs F-xx`. `⚠️ … 이미 진행 중인 원격 브랜치`가 나오면(develop에 머지 안 된 다른 원격 브랜치에 `feature/F-xx-*`나 develop과 다른 `docs/specs/F-xx-*.md`가 있음) **새로 쓰지 말고 멈춘다**. 내 브랜치면 그 브랜치로 `git switch`해 이어 가고, 상대 브랜치면 사용자에게 묻는다 (11-19 내 다른 PC의 F-14 진행이 develop의 NOW에 가려 spec을 중복 승인한 사례, #54). `ℹ️ (지금 브랜치)`와 `ℹ️ … squash 머지 뒤 남은 브랜치`는 멈추지 않는다. `❓ 판정 불가`(exit 1)나 `⚠️ git fetch 실패`가 나오면 통과로 보지 않고 멈추고 묻는다.
2. **근거 수집** — `docs/기획서.md`에서 **필요한 부분만** 읽는다 (Grep으로 위치를 찾고 해당 범위만 Read):
   - 기능 목록 표의 해당 행, 핵심 사용자 시나리오, 화면 목록의 관련 행
   - 주요 API 표에서 관련 행, ERD에서 관련 테이블, 아키텍처의 관련 설명(분석 파이프라인, 추천 알고리즘 등)
   - `docs/결정로그.md`에서 관련 결정
   - 의존하는 기존 spec(예: 로그인), `docs/conventions.md`
   - **🔴 차단(`blocker`) 이슈가 열려 있으면 spec을 쓰기 전에 멈추고 사용자에게 묻는다** (hook 주입 "열린 follow-up 이슈"의 차단 그룹, 영역 무관). 이 기능이 그 이슈에 막히는지, 먼저 해결할지 정한다.
   - 열린 follow-up 이슈 중 이 기능과 겹치는 것: `gh issue list --label follow-up --state open --search "F-xx"`와 hook이 주입한 내 영역 이슈 목록. 이 기능에서 함께 고치는 게 자연스러운 것은 사용자에게 흡수 여부를 묻고, 흡수하면 spec 헤더 "관련 이슈"에 적고 수용 기준으로 옮긴다 (11-19 F-07이 #19·#21을 흡수한 선례). 구현 PR 본문에 `Closes #n`을 적어 머지 때 닫는다.
3. **초안 작성**: `docs/specs/_TEMPLATE.md`를 복사해 `docs/specs/F-xx-<영문-slug>.md` 생성.
   - 수용 기준은 **정상 흐름 + 검증 실패 + 권한 + 경계값**을 포함해 보통 4~10개. 각각 테스트 1개 이상으로 옮길 수 있어야 한다.
   - API 계약은 요청·응답 JSON **예시를 실제 값으로** 쓴다. 에러 코드는 conventions의 체계를 따른다.
   - DB 변경이 있으면 필요한 Flyway 파일 이름과 DDL 요지를 적는다.
   - AI 기능이면 6절(LLM)을 채운다: 프롬프트 파일, 출력 JSON 스키마, mock fixture 경로, 캐시 정책.
   - 7절 테스트 계획에서 AC → 테스트 위치를 매핑한다.
   - 범위 밖을 명시한다 (P1/P2 기능이 끼어들지 않게).
4. **반대 의견**: 다음이면 근거와 함께 지적하고 대안을 제시한다.
   - 기획서의 일정(마일스톤) 대비 범위가 과함
   - 기획서와 conventions, ERD 사이에 모순
   - 테스트할 수 없는 수용 기준 ("빠르게", "적절히")
5. **질문**: 기획서로 결정할 수 없는 것만 AskUserQuestion으로 2~4개씩 묻는다. 선택지에 `(추천)`을 붙이고 근거를 짧게.
   답을 받으면 spec 본문에 반영한다. 기획서 수준의 결정이면 `docs/결정로그.md` 맨 아래에 한 줄 추가한다 (기존 행은 고치지 않는다).
6. **DRAFT로 저장**하고 사용자에게 요약(수용 기준 목록, API, DB 변경, 범위 밖)을 보여 주며 승인을 요청한다.
   내 NOW 파일(`node scripts/stamp.mjs --file`)을 갱신한다 (현재 기능 = 이 spec, 다음 할 일 = 승인 대기). 갱신 줄은 `node scripts/stamp.mjs --now`.
7. **승인 처리**: 사용자가 승인하면 헤더의 상태를 `APPROVED`, 승인 칸에 `<사람> YYYY-MM-DD`를 적는다.
   커밋: `docs(F-xx): spec 승인`. (브랜치가 main/develop이면 `feature/F-xx-slug`를 만든 뒤 커밋) 내 NOW 파일과 함께 `git push -u origin <브랜치>`로 올려 상대가 착수 사실을 보게 한다.

## 기준

- spec 하나는 PR 하나 크기 (1~3일). 크면 F-xxa, F-xxb로 나누자고 제안한다 (예: F-05a ZIP, F-05b URL. 파일 `docs/specs/F-05a-slug.md`, 브랜치 `feature/F-05a-slug`, 커밋 범위 `F-05a`).
- 기획서 "명세서 구조 매핑"에 걸린 기능(회원 CRUD, 분석 CRUD, 챌린지, 게시판·댓글 CRUD)은 명세서가 요구하는 동작(예: 수정·삭제, 목록·상세)이 수용 기준에 빠짐없이 들어갔는지 확인한다.
- 새 API의 Swagger Tag를 `docs/conventions.md` 8절 목록에서 고른다.
- AI가 혼자 승인 상태로 바꾸지 않는다. 반드시 사용자의 명시적 승인이 있어야 한다.
- spec 8행 영역 오너는 실명으로 쓴다 (A 김동환 / B 김준섭).
- 승인 커밋과 NOW 파일 갱신이 끝나면 사용자에게 `/clear` 후 `/implement F-xx`를 새 세션에서 시작하도록 권한다 (CLAUDE.md "세션 운영". spec 파일과 NOW 파일이 상태를 들고 있다).
