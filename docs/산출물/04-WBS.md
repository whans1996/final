# WBS (Work Breakdown Structure) — 바이브노트

> 작성 상태: ✅ 초판 (2026-11-17) · 실적 갱신 2026-11-26 · **재계획 2026-11-25** (2차 기획, 4절 재조정·6절 추가) · **로드맵 반영 2026-11-27** (6절을 로드맵 항목으로 다시 씀) · 일정 정본은 `docs/로드맵.md`(R-1). 이 문서는 제출용 WBS · 간트 차트: [05-간트차트.md](05-간트차트.md) (같은 WBS ID 사용)
> 담당 = **영역 오너**(구현·머지·최종 확인). 11-19부터 영역별 병렬 개발이다. **A = 김동환**(AI·분석·학습 루프), **B = 김준섭**(카드·소셜). W1 기능(3.1 등)은 릴레이로 함께 구현했다. 3.8·3.15는 11-19에 B → A로 옮겼고, 11-26에 팀(`team`, F-20a~c)·시드 카드 생성·검수(K-3)·관리자 검수 화면(S-1)과 A 기능의 FE도 A로 옮겼다 (`docs/결정로그.md`, `docs/기획서.md` 7.5절).
> 6절 상태·실적·기간은 기능 PR이 완료 표시 커밋에서 **자기 항목 행**을 바로 고치고(일찍·늦게 끝나면 뒤 항목 재조정 포함, 결정로그 11-27), 주간 `/progress`는 빠지거나 어긋난 것만 develop 기준으로 맞춘다.
> 상태: ✅ 완료 · 🟡 진행 중 · ⬜ 미착수. **기간** = 계획(기준선), **실적** = 실제 시작~완료일과 근거(PR).

## 일정 관리 방식

- 계획 기간은 11/17 초판 기준선으로 고정하고, 실제 진행은 **실적** 열에 적는다 (최종 보고서의 계획 대비 실적 자료).
- 기능 PR이 develop에 머지되면 해당 행의 상태·실적을 고친다 (`/pickup`의 머지 후 정리, `/progress` 주간 점검).
- 계획 날짜를 다시 잡는 것(재계획)은 `/progress`가 마일스톤(M1 12/07, M2 12/14) 위험을 판정했을 때와 2차 기획(기획서 6절)을 반영할 때만 하고, 바꾼 이유를 `docs/결정로그.md`에 남긴다. 바뀐 계획은 기간 열에 `~~기준선~~ → 재계획`으로 적어 기준선을 지우지 않는다.
- **11-25 재계획**: P0 21개를 11/24에 끝내(M2 기준선보다 20일 앞섬) 2차 기획을 확정했다. 4절(테스트·품질)을 2차 검증 트랙(V-1~V-5)과 디자인 개편(F-29)으로 재조정하고, 6절(2차 개발)에 하네스 개편과 AI·UI 확장을 추가했다. **12/14에 T0·T1 기능을 동결**하고, T2는 W5(12/15~12/20)에 티어 순서대로 남는 시간만큼 하다가 12/20에 멈춘다. ID(H-1·F-26~F-33 등)는 기획서 6절 2차 백로그와 같다.
- **11-27 로드맵 반영**: 11-26부터 일정 정본은 `docs/로드맵.md`(기간 × 사람 × 트랙, 넘겨주는 시점)다. 6절은 로드맵 항목 표를 제출용으로 옮긴 것이라 ID가 로드맵 ID이고, 기간·담당·의존은 로드맵을 따르며 로드맵이 바뀌면 함께 맞춘다. 로드맵은 항목이 일찍 끝나거나 늦어지면 실제 날짜로 고치므로(끝난 항목의 끝 = 머지일, KST) 6절의 완료 항목 기간은 실제 기간이다. 상태는 `node scripts/roadmap.mjs`가 PR 본문 `Roadmap: <ID>` 줄로 계산한 값이다. 1~5절의 기준선·실적은 그대로 둔다.

## 6. 2차 개발 (11-25 재계획 추가, 11-27 로드맵 반영)
